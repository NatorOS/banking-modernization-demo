# Security and deployment notes

## Credentials

- No credentials are in code, configuration, logs or this repository. `.gitignore` excludes
  `.env*`, `*.key`, `*.pem`, `credentials*`, `data/` and `output/`.
- Locally, the simulator's HMAC key is generated per checkout in `data/webhook.key` (mode
  0600, git-ignored), or read from `WEBHOOK_HMAC_KEY`.
- In AWS, the key is generated by CloudFormation into Secrets Manager (`GenerateSecretString`).
  Only the ARN is ever output. The Lambda role can read that one secret and nothing else.
- Deploy and teardown run under the operator's own scoped AWS profile. Both scripts verify the
  account ID (and deploy also verifies the region) before making changes. No admin keys are
  requested or embedded.
- The Column sandbox secret is **not** read or used. The Column adapter is omitted until scoped
  access exists and the current Column API and webhook documentation has been verified.

## API access and webhook authenticity

- Every route (`ANY /api/{proxy+}`) uses `AWS_IAM` authorization, so callers must sign with
  SigV4. The local dashboard (`modern.server --remote`) and CLI (`modern.demo --remote`) sign
  with botocore using the operator's profile. The browser never sees credentials, and the proxy
  binds to `127.0.0.1` only.
- Provider events must carry `X-Provider-Timestamp` and `X-Provider-Signature: v1=<hmac>` over
  `"<timestamp>.<raw body>"`. They are verified with a constant-time comparison and a 300 s
  replay window before parsing. Replays inside the window are caught by event-ID idempotency,
  and same-ID payload tampering is rejected (`event_conflict`). This is the simulator's scheme;
  a real provider's documented scheme (and possibly its IP ranges or mTLS) must replace it.
- Input limits: 16 KiB request bodies; strict validation of namespace, IDs, integer cents,
  currency and return codes.

## Network boundaries and data egress

- There is no VPC, so there is no NAT gateway and no inbound ports. Lambda talks only to
  regional AWS service endpoints (DynamoDB, Secrets Manager, CloudWatch Logs).
- The simulator runs inside the Lambda, so **no third-party egress** occurs. A real provider
  adapter would add outbound HTTPS to the provider. A bank deployment would route that through
  controlled egress (VPC with endpoints, firewall allowlist).
- IAM confines the Lambda to partition keys `NS#demo-*` in the foundation table
  (`dynamodb:LeadingKeys`). It has no `Scan` and no access to other tables.

## Logging

Lambda emits one JSON line per request: route, method, status, latency and request ID.
API Gateway access logs record the request ID, route, status, latency and caller identity.
Request bodies, headers, signatures, idempotency keys and secret values are never logged.
Retention is 7 days.

## What a real bank would still require

- Contract-verified provider adapter: the provider's documented idempotency semantics, webhook
  signature scheme and event catalogue, and a sandbox certification run.
- Bank identity integration (SSO or a federated IAM Identity Center) and least-privilege roles
  per persona, with separation of duties for reset, purge and deploy.
- Production data controls: KMS customer-managed keys, PITR and backups on the table,
  retention and legal hold, and data residency.
- An event intake that does not require IAM from the provider (signature-only route or a
  provider-specific authorizer), plus a dead-letter or exception queue for rejected events
  with an operator workflow.
- Formal reconciliation against the provider's statements and the bank GL, with tolerances,
  sign-off and break management.
- Observability and alerting (alarms on rejects, pending age and contention), a threat model,
  penetration testing, change management, DR and runbooks, and model-risk and audit review.
- A multi-currency, fee and FX model if needed. This demo is USD-only, single-account and
  single-currency.
